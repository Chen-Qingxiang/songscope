# 01　概念模型：宋史世界由什么组成

## 1.1 六层模型

SongScope 将历史知识分为六层：

```text
现实与历史对象        Entity / Concept
发生与变化            Event / State
对象之间的结构        Relation / Participation
史料中的陈述          Assertion
支持或反驳的材料      Evidence / Source
面向研究的结果        Projection / View / Interpretation
```

这些层必须分开。最常见的数据错误，正是将它们混在一起：

- 把人物当前简介当成永久事实；
- 把一次任命动作当成整个任期；
- 把史料作者的评价当成系统结论；
- 把现代坐标当成古代行政区本身；
- 把研究者根据多条证据推定的日期伪装成史料明载日期。

## 1.2 Entity：具有可持续身份的对象

`Entity` 是在一定语境中可以被持续识别、被不同事件引用的对象。

核心子类：

- `Person`：人物；
- `Group`：家族、朋党、军队、使团等群体；
- `Place`：地点的持续空间身份；
- `AdministrativeUnit`：具有历史有效期的行政区实例；
- `Institution`：官署、学校、书院、寺观、军镇等机构；
- `Office`：官职、职名、差遣、阶官、爵位等制度性位置；
- `Work`：诗、词、文、书信、奏议、史书等知识作品；
- `SourceObject`：某一版本、卷册、碑刻、影像或数字资源；
- `MaterialObject`：建筑、器物、碑石、河堤等物质对象；
- `Polity`：宋、辽、西夏、金等政治体；
- `Concept`：制度、政策、思想主题、灾害类型、文体等受控概念。

### 不采用“万物都塞进一张表”

系统可以有统一的 `entity_registry` 提供全局 ID、类型和生命周期状态，但每类对象仍应有明确的子类型表和字段约束。统一身份不等于放弃类型。

例如：

```text
entity_registry
  ├── person
  ├── place
  ├── institution
  ├── office
  ├── work
  └── source_object
```

## 1.3 Event：历史中的发生与变化

`Event` 表示在时间中发生、导致参与者状态或关系发生变化的过程。

典型事件：

- 出生、死亡、婚姻、迁居；
- 科举应试、登第、入仕；
- 除、授、迁、转、改、罢、落、夺、复、起；
- 实际到任、离任、兼任、权摄；
- 战争、会盟、使节往来；
- 灾害、赈济、修堤、捕蝗；
- 写作、刊刻、赠答、唱和、通信；
- 立法、改制、奏议、审判、诏令；
- 建造、修缮、毁坏、迁移。

事件可以嵌套：乌台诗案是一个复杂事件，其中包括弹劾、逮捕、审讯、判决、贬谪等子事件。

## 1.4 State：持续一段时间的状态

不是所有历史信息都应建成瞬时事件。`State` 表示在一段时间内成立的情况，例如：

- 苏轼居于黄州；
- 某人处于丁忧期；
- 某行政区隶属于京东东路；
- 某人担任某项实际差遣；
- 某部书在某时期被禁毁；
- 某地处于旱灾或围城状态。

事件与状态通常成对：

```text
任命事件 ──creates──> 任职状态
罢免事件 ──ends─────> 任职状态
迁居事件 ──creates──> 居住状态
```

## 1.5 Participation：事件中的角色

人物与事件不应只有模糊的 `related_to`。参与关系必须具有角色：

```text
EventParticipant
- event_id
- entity_id
- role_type
- side / faction
- sequence
- temporal_extent
- evidence
```

例如徐州水灾事件中：

- 苏轼：地方长官、组织救灾者；
- 武卫营卒长：受请求的军事参与者；
- 富民：拟离城的社会群体；
- 徐州城：受威胁对象；
- 黄河洪水：致灾过程。

## 1.6 Relation：跨事件或持续成立的结构

`Relation` 适用于具有独立研究意义、不能只通过单个事件完全表达的联系：

- 亲属与婚姻；
- 师生、同年、同乡；
- 长期同僚或政治联盟；
- 机构隶属；
- 行政区上下级；
- 作品之间的引用、唱和、改写；
- 版本之间的派生关系。

关系必须能够记录方向、有效期、证据和成立机制。

## 1.7 Assertion：关于上述对象的可争论陈述

`Assertion` 不是“事实本身”，而是一个来源、整理者或算法提出的陈述。

例如：

```text
subject: person/su-shi
predicate: held_office
object: office/zhimizhou
valid_time: 1074~/1076?
```

该陈述还不完整。必须知道：

- 谁提出或整理了它；
- 来源是哪一版本的哪一段；
- 史料是直接明载还是根据上下文推断；
- 日期是原文、换算还是估计；
- 是否存在冲突断言；
- 当前是否被项目采纳为默认解释。

## 1.8 Projection：用于分析的投影

前端所见的“人物履历”“地图路线”“关系网络”不是新的事实层，而是对同一知识库的投影。

例如：

- `career_timeline`：按时间投影任命和任职状态；
- `mobility_path`：按时间投影地点状态；
- `social_network`：按关系类型和时间窗投影网络边；
- `disaster_response`：将灾害事件与治理事件配对；
- `office_flow`：将任职状态聚合成官职流动矩阵。

投影可以删除、重算和升级；原始断言与证据不能因此丢失。

## 1.9 与现有标准的关系

SongScope 借鉴 CIDOC CRM 的事件中心思想、W3C PROV-O 的来源追踪模式、EDTF 的不确定日期表达以及 Linked Places 的时态地名思路，但第一阶段使用领域友好的关系型 schema。

原则是：

> **内部模型必须能映射到通用标准，但不要求所有整理者直接操作通用本体。**
